# ADR 0039: Allocation dispute correction screen

- Status: Accepted
- Date: 2026-11-09

## Context

ADR 0038 stores one full reversal for an upheld dispute and does not add a screen. The operator still needs to see the stored correction, or confirm the full amount before sending that command, and a lost HTTP 200 must not mint a second reversal.

## Decision

The existing `/allocation-disputes` screen shows the correction section for `DevelopmentJwt` only. A stored correction is shown as stored. `upheld` with `correction: null` and reversal context `confirmed` offers one full reversal. The section shows the allocation id, the full amount, and the currency from `GET /api/allocations/{allocationId}/reversal-context` before the operator confirms. The reason uses React Hook Form and Zod and is normalized with the same `string.Trim()` rule as the API, 1–500 UTF-16 code units. Reversal context `reversed` together with a successful correction GET whose `correction` is `null` means this dispute has no link. It does not offer another reversal. A failed correction GET does not show that message and offers the same read again.

Before the browser creates the descriptor, the click checks the current QueryClient reads against the current epoch, visit, dispute, and allocation. It requires a successful detail read and successful, idle reads of the decision, the correction, and the reversal context. Retained data after an error or during a refresh does not authorize the command. The decision read is the resolution query updated by the decision write. The reversal-context key includes the dispute, so two disputes of one allocation do not share one observation. The browser writes `finopsdesk.allocation-dispute-correction-attempt`, bound to the organization, `developmentJwt`, and the normalized `sub`, before POST. HTTP 200 is accepted only when the dispute, allocation, invoice, bank transaction, normalized reason, amount, currency, stored actor, and a real .NET timestamp match that record, the status is `reversed`, and `replayed` is a boolean. Amounts stay decimal strings through `lossless-json`, `readMoney`, and `DecimalString`. The current actor does not replace the stored actor. A defective HTTP 200 leaves the original key and body uncertain.

GET parses and shows the stored amount, currency, reason, actor, and time. A GET does not settle an attempt. The agreed 400, 401, 403 `reconciliation.actor.required`, 404, and 409 pairs reject an attempt that is not already uncertain. A later refusal keeps an earlier uncertain attempt. An abort, a network failure, HTTP 500, and an unreadable body leave the attempt uncertain. A failed write before send does not send. A failed uncertain mark leaves the previous record. After a verified POST, another correction stays blocked until that descriptor is removed and the correction read is refreshed. If removal fails, the module remembers that result and offers only another removal of the same attempt. Replay of that attempt is blocked. Parallel clicks during a send are rejected. Success, failure, and the refresh warning belong to the epoch, panel instance, and visit that sent the command. Descriptor settlement does not depend on the panel staying mounted. A refresh error keeps the confirmation and offers another GET of that correction. A late refresh does not replace a newer warning.

Abandon requires a later successful GET of the detail, the decision, the correction, and the reversal context. Each of those reads must have started after the abandon. `dataUpdatedAt` records when a result is written into the cache, so a GET that started earlier and finishes later does not reopen the form. Successful removal of the visible dispute's tracking raises that boundary and starts those four GETs. An older in-flight request is cancelled first, so the replacement reads do not reuse it. The form opens when the replacement reads succeed. An older epoch does not confirm a newer one. An attempt for dispute A remains an attempt for A across A → B → A. A verified POST invalidates the financial cache, the dispute work summary, and the `needs-correction` queue for that epoch through `invalidateVerifiedReversal` immediately, before the correction GET settles. A failed correction GET keeps the confirmation and offers that GET again. `ProductionCookie` does not mount the section. `Operator` does not gain `allocations.reverse`. The cookie allowlist, flags, capability map, and session contract v2 stay unchanged.

## Consequences

Chromium proves the lost-response case only after SQL Server shows one reversal, one correction, and one reversal audit. The same key and body are replayed. Those counts stay at one. Partial reversal, a bank refund, and rebooking remain outside this phase.
